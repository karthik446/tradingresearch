Labs spike v3, not published. Part of [week 1 labs](index.md). Next: [lab w1l2](w1l2.md).

**What you build:** the four checks in `check_one` that reject a claim and say why. The author's tag already has them; here they are removed, and you put them back one at a time against the author's own model replies. **Start:** `tr lab start w1l1` on your clone at `week-1-start`, after `uv sync`. **Cost:** $0. No key, no model call.

> **The repo's own suite is red until w1l1.4 is green.** The lab w1l1 stubs remove the checks in `check_one`, and `tests/test_analyze.py` covers them. So `uv run pytest -q` fails 4 tests on the w1l1.1 stub, 3 on w1l1.2, 2 on w1l1.3, 1 on w1l1.4 and none once w1l1.4 is green (labs spike report `READ-V2.md`, outside this repo, finding 4). This is expected; the `lab` marker cannot help, because the failing tests are the repo's, not the lab's. `tr lab verify` runs only the exercise's check, and `tr lab next` runs the whole suite only at the end of a lab, so it is green by then. Labs w1l2-w1l4 keep the suite green (61 passed, 1 skipped on this branch, the runner's own tests included).

**Reading folded in (not exercises):** the reply format (`claims`, each with `id`, `tag`, `text`, `value`, `source_ids`, `derived_from`), the prompt's SOURCES table and how `validate_claims` calls `check_one` per claim. All three are in the build guide `week-1.md` §1-§2 (outside this repo); the concept entries below give the one-paragraph version.

### w1l1.2 number_in_text

**Concept.** The model writes numbers only in `value`, and the text says `{value}` where the number goes. A digit anywhere else in the text is a number no code checked. Three digit forms are allowed because they are not measurements: `{value}`, a `YYYY-MM-DD` date and a table name such as `sma_200`. The start code has `ALLOWED_DIGITS` for exactly those. [Claim check](concepts.md#claim-check).

### w1l1.3 placeholders

**Concept.** The renderer fills one placeholder, `{value}`, from the claim's `value`. Any other `{...}` is left as literal braces in the analysis (bad_placeholder). `{value}` with a null value renders as nothing; in this run it is the model putting a label ("bull-high") where a number goes, taxonomy class 5. [Claim check](concepts.md#claim-check), [failure taxonomy](concepts.md#failure-taxonomy).

**You edit** `check_one` ([stub](../exercises/w1l1.3-placeholders/stub/src/tradingresearch/analyze.py)):

**FAIL messages:**

- `KO 2026-11-12 c9 'The SPY market regime is labeled {value} on this date, which is bull-high.' has {value} but value is null (the regime is a label, not a number), yet it was kept.`
- `'labeled {label}' uses a placeholder the renderer never fills: expected ('bad_placeholder', '{label}') (the other placeholders, sorted, joined by ', '); got None`

A placeholder the text repeats, such as `{foo}` twice, may be listed once or twice in the detail: either is accepted.

### w1l1.4 cascade

**Concept.** An inference lists the claims it stands on in `derived_from`. If one of them was rejected, the inference has no checked ground, so it goes too: `bad_derivation`. It is a consequence, not a separate failure: in [lab w1l2](w1l2.md) you note the parent's failure, not the cascade. [Claim check](concepts.md#claim-check), [failure taxonomy](concepts.md#failure-taxonomy).

**You edit** `check_one` ([stub](../exercises/w1l1.4-cascade/stub/src/tradingresearch/analyze.py)):

```python
    if tag == "inference":

        #   with bad_derivation: "derives from a rejected or later claim: c5" when every missing id is a claim
        #   of this reply (`ids`), else "unknown claim id: c99". Missing ids in derived_from order, joined by ", ".
```

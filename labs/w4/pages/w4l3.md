### w4l3.1 the tools arm is a Run

**Concept.** Core `run` gives a fixed arm a contract: before the first call it asks the budget whether the whole run fits (`budget.plan`), every call is reserved on that budget before it is sent, only a succeeded sample is graded, a grader that raises `CannotGrade` leaves no score, and the record counts what the model calls cost. `run_tools` has to keep the same contract around the loop. The stub keeps none of it: it plans nothing, hands the loop the bare provider, grades every sample, and records one call per sample and $0. The plan uses each item's first request as the loop sends it (system turn, tools prompt, tools offered); it cannot know how many calls each loop will make, which is why every later call is reserved too. [Tools arm](concepts.md#tools-arm), [Budget plan](concepts.md#budget-plan).

### w4l3.2 the tools arm in the experiment

**Concept.** `run_arms` runs every arm of a config on one dataset and stores each parsed sample as an `Analysis`. The stub still refuses any config with a tools arm. A `mode = "tools"` arm gets its `Run` from `run_tools`, on the arm's own provider (pinned when the arm is); a fixed arm stays on core `run`, with the same graders. Only a code grader reads a tool loop (a model grader is shown the final answer, not the calls), so a config that puts any grader that is not code beside a tools arm is refused before the first arm runs, when nothing has been spent. And the route stored with each analysis is looked up under the exchange's first user turn: for a fixed arm that is the item's prompt, for a tools arm the item's tools prompt; asking under the item's prompt gives `openrouter:unknown`. ### w4l3.3 the tool-call grader

**Concept.** The other graders read the final answer; `tool_calls_ok` reads the calls that led to it. It walks them in the order they were made and stops at the first fault, with 0.0 and the fault's name first in the explanation: `tool_error` (the call raised, or its result is an object with an `"error"` key, whatever the key holds, held parsed or as the JSON text the model was sent), `repeated_call` (the same tool with the same arguments, compared as JSON, so key order and spacing do not matter; the order inside a list does), then `too_many_calls` past `max_calls`. The cap ranks last: a loop with an erring or a repeated call reports that call, even when it also goes past the cap. `max_calls = 2 × len(TOOLS) = 6`: every tool once plus one follow-up each; more is a loop, not a lookup. A loop with no tool calls scores 1.0, by design, so `compare` keeps the grader when the fixed arm has none. The stub scores 1.0 on everything and its cap is 0. [Tool-call grader](concepts.md#tool-call-grader), [First fault](concepts.md#first-fault).

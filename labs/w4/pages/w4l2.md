**The data.** The one recorded tool exchange, copied into [`data/`](../data/): `turn1.request.json` (the first request: the FAKEA ticker-day of lab w4l1, one tool offered, the capture's own `get_sources`), `turn1.reply.json` (a reply that calls it once, id `toolu_01FAABR9tQJYBK8Xr5g6ZhrU`), `turn2.request.json` (the call answered) and `turn2.reply.json` (the final JSON, 11 claims). The two calls cost $0.022888 when recorded. [`tools/fakea.py`](../tools/fakea.py) also has two edited replies, one that asks for your three tools at once and one that asks for one more, and two failures: an HTTP 400 and an HTTP 503 (which the adapter retries once).

**Why the checks compare against the recorded request.** A replayed reply cannot react to what you send: the recorded final answer comes back even if your request is wrong. So a run is evidence about your loop only where your requests equal the ones that produced the replies, and the w4l2 checks compare them field by field. For the recorded exchange the checks put `get_sources` back as the only tool, answering with the recorded rows, so the model's call to it has an answer. Two parts still differ by design: your user turn (the recorded one told the model to use `get_sources`) and the tool turn's text (the capture's tool answered in plain lines; a tool span keeps a result as JSON, so the same lines come back wrapped in JSON).

**What observe can and cannot show.** `observe.py loop` prints the length of `tools_prompt`'s turn and how many source rows it holds, then runs `analyze_with_tools` five times: the recorded exchange (each request beside the recorded one), the three-call reply, a model that never stops asking (`max_turns` 3), an HTTP 400 on the second call, and an HTTP 503 before every reply. For each: requests sent, tool turns, the sample's outcome, parse status, error and claims, and the kinds of span in the trace. It shows what your loop sends and keeps; it cannot show how a real model would answer a different request. The checks decide.

### w4l2.3 the cap and the trace

**Concept.** Nothing in the conversation makes the model stop asking; only the loop can. The stub's `while True` has no cap, so a model that always asks for a tool keeps it calling: in observe it stops at 13 requests only because the replay gives up there, and the sample still reads succeeded. At most `max_turns` model calls: if the last allowed reply still asks for tools, the sample fails with the error code `max_tool_turns`, returned, not raised. A failed call (an HTTP 400) ends the loop the same way, with that call's error; a spending cap's refusal stops the whole run and reaches the caller. And each model call is a span, written when it ends: before the tool calls it asked for, with the trial span last, so a run stopped halfway still shows the calls that cost money. [Turn cap](concepts.md#turn-cap), [Tool trace](concepts.md#tool-trace).

> **Until this exercise is green, do not run `pytest tests/test_week4.py`**: its cap test never ends on this stub (see the top of this page). The check below and observe end.

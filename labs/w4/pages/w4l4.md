### w4l4.1 one known provider

**Concept.** A route says who served a call: the client, then the host, sometimes a tier after it (`openrouter:deepinfra/fp8/flex`). A record the teacher arm writes may become training data, and the teacher terms filter needs to know which provider served every turn; so a trainable record must carry a clean route, one known provider behind the openrouter client. Unknown (in any case, at a tier too), any `mixed(...)` log, even one that names a single provider, a host behind another client, the client with no host, and the empty route are not clean. The stub calls every route clean, so all of them reach the training set. A restricted record never needs to say who served it and keeps any route. [Provider route](concepts.md#provider-route), [Provenance](concepts.md#provenance).

### w4l4.2 the route of the exchange

**Concept.** The adapter logs the route of every call under a key, and `route_for(prompt)` reads it back when an analysis is stored. In the stub the key is the request's last turn, which in a tool loop's follow-up is the tool result: only the first call's route lands under the item prompt, so a loop served by Azure then Google reads as Azure. The key that every request of one loop shares, and two items never do, is the exchange's first user turn. A request with only system and user turns opens a new exchange, so the item's old routes stop counting even if the new call fails. A retried follow-up is the same turn of the same exchange, so the routes logged before it stay. `route_for` then sums the exchange up: unknown when nothing was served or any turn's route is not clean, the route itself when every turn agrees, otherwise `openrouter:mixed(a+b)` with each provider once, in sorted order. A reply whose provider is null is unknown, not a provider named None. And an arm pinned to one provider gets its own log, so arms never see each other's routes. [Provider route](concepts.md#provider-route), [Exchange](concepts.md#exchange).

**You edit** `exchange_key`, `routed`, `route_for` and two places in `invoke` ([stub](../exercises/w4l4.2-the-route-of-the-exchange/stub/src/tradingresearch/openrouter.py)):

### w4l4.3 the first rule change

**Concept.** Champion/challenger runs the current rules (the champion) and one changed rule (the challenger) side by side on the same analyses, and adopts the change only if it wins by a rule fixed before the first session it covers. Fixing that rule first is pre-registration: the metric, the pass rule, the guard, the margin and the sample size are written down, with a time, before any result exists, so nobody can tune them after seeing results; the journal refuses to change them later. The change here is `short-sma50-trend`, a `Filter`: on the short horizon it drops a long below the 50-session average and a short above it (`dist_sma_50_atr` carries the sign, and the sign decides however small the distance), drops a thesis whose value is missing because nobody can show it is with the trend, and keeps one exactly on the average; other horizons pass untouched. The challenger reaches a rule only through the reviewed registry `CHALLENGER_RULES`, and the change file names that entry. The registration time falls after the 2026-11-16 open (14:30 UTC) and before the 2026-11-17 open, so the first session covered is 2026-11-17. [Rule change](concepts.md#rule-change), [Pre-registration](concepts.md#pre-registration), [Challenger](concepts.md#challenger).

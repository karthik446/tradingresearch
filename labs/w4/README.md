# Week 4 labs: the folder

This folder holds week 4 of the AI engineering track, run by `tr lab` on this repo from the tag `week-4-start`: 12 exercises in 4 labs. Part A is labs w4l1 (three tools the model can use) and w4l2 (the tool loop), the code of the chapter's §2 and §3. Part B is labs w4l3 (the tools arm in the experiment runner and the `tool_calls_ok` grader, §3) and w4l4 (route provenance and the first rule change, §5 and §6). A learner starts at [pages/index.md](pages/index.md); how `tr lab` works is in [labs/README.md](../README.md). This page is for whoever maintains the folder.

`PROOF.md` and each exercise's `expected_output/` (`fail.txt`, the stub's red run, and `pass.txt`, the solution's green run) are not in the folder yet: they are written by the commands in [Prove the folder](#prove-the-folder) once the folder's review is done. Week 4 has no `session/`.

**The base.** `base = "week-4-start"` makes the first `tr lab start w4l1` set the repo's files to that tag and commit them, so week 4 does not depend on the learner's week-3 code. `week-4-start` has no `tools.py`, and its `analyze.py` has no `tools_prompt` and no `analyze_with_tools`. The w4l1.1 stub brings in the week's `tools.py` with the schemas, the error handling, the cited row and the `names` filter cut out; the w4l2.1 stub brings in the week's `analyze.py` with `tools_prompt`, the tools on the request, the answers, the cap and the span writes cut out. `MAX_TOOL_TURNS`, `_model_span` and `_tool_span` come with it. In part B the first stub of each file does the same: w4l3.1 brings the week's `experiment.py` (`run_tools`'s contract and the tools arm in `run_arms` cut out), w4l3.3 `evals.py` (`ToolCallsOk`'s walk and cap), w4l4.1 `records.py` (`clean_route`, the trainable-route refusal), w4l4.2 `openrouter.py` (the exchange key, the per-exchange route, the pinned arm's own log, the null provider), w4l4.3 `rules.py` (the filter and its registry entry) and `experiments/rule-change-1.toml` (its description and hypothesis only).

**The data.** All six files in `data/` are byte copies of the repo's `tests/fixtures/week4/` at `week-4-start`. Only the two replies are model output: one exchange recorded on 2026-11-17 with `anthropic/claude-sonnet-5.5`, offered the capture's own tool `get_sources(groups)` with `tool_choice` auto. It called the tool once and answered with 11 claims on the second call; the two calls cost $0.022888 (the chapter's §2 has the turn-by-turn numbers). The capture's tool is not one of the three the labs build, so the exchange can only be replayed with `get_sources` put back (`fakea.capture_tool`). `models.json` is the model's `/models` row recorded with the exchange; `fakea.prices` turns it into the price the w4l3 budget plans with.

**The replay.** `tools/fakea.py` swaps the OpenRouter adapter's HTTP transport for an `httpx.MockTransport`, and `fakea.replaying` answers request i with `answer(replies[i])`: `turn1` and `turn2` (the recording), `three_calls` (the first reply edited to ask for `get_indicators`, `get_levels` and `get_fundamentals` at once), `one_more` (one more `get_indicators` call), `failed` (an HTTP 400) and `busy` (an HTTP 503, which the adapter retries once). From the 13th request on (`STOP_AFTER = 12`) the replay answers HTTP 400, so a loop with no cap still ends under the lab checks and observe. `fakea.Capped` is a spending cap that refuses after a given number of calls with `BudgetExceeded`. `fakea.context(extra=True)` gives every value extra digits (a close of 101.40124722), to tell a tool that rounds the way the SOURCES table does from one that does not.

**Part B's helpers.** `fakea.other` is the FAKEA context under the ticker FAKEB, a second item whose tools prompt differs from the first, so a run has two exchanges. `fakea.experiment` writes and loads a config with one arm per mode, the recorded model and prompt, and the session 2026-11-13. `fakea.costless` strips `usage.cost` from a replayed reply, so the budget keeps its own estimate; `fakea.cost_of` is the cost a reply kind reports. w4l4's checks and observe build records with the repo's own `tests/factories.py`.

**The offline guard.** The labs claim $0 and no network, so `tools/offline.py` enforces it: `conftest.py` installs it before any test module imports learner code, and `observe.py` before it imports `fakea`. Socket connections, DNS lookups, subprocesses, os spawns and the real httpx transports raise `Blocked` and are recorded; the `httpx.MockTransport` the checks use is not touched. It is an honor-system check, not a sandbox: it catches a learner's code that reaches for the network by accident, in the same process; code that sets out to get around it can.

## Prove the folder

From the root of a clean clone (`uv sync` done):

```bash
uv run python labs/tools/prove.py w4 > labs/w4/PROOF.md
```

It copies the clone into temp folders and runs the chain (each stub red with `red_expect`, `solution.diff` green, earlier checks of the same lab still green, every `wrong/*.diff` red with its `expect:`), the end state (the twelve `[end]` files equal `week-4-end`), the hint guard, the captured output and a runner smoke; [labs/w1/README.md](../w1/README.md#prove-the-folder) describes each row. It exits 1 if any row reads NOT PROVEN. Until the captures below are written, the 24 captured-output rows (`expected_output/fail.txt` and `pass.txt` of each of the 12 exercises) read NOT PROVEN. Re-run it after changing an exercise, a stub, a test message, the data, observe or `lab.py`.

The hint guard is a string match: it rejects a hint that repeats a `solution.diff` added line of 12 or more characters, or holds a code fence longer than one line. It does not judge whether prose dictates the answer; that is a reading job. The week-4 hints state the idea, with no code; a hint may name a function the stub already calls (`budget.plan`, `run_tools`, `route_for`), never the change to make.

**Captures for the site.** The same as week 1's (see [labs/w1/README.md](../w1/README.md)), without a session: each exercise's `expected_output/fail.txt` and `pass.txt`, and the page text in each `exercise.toml`: `goal`, `what_tested`, `writes`, `show_tests` (no `show_data`), with `goal` and `section` per lab in `lab.toml`. `python labs/tools/capture.py w4 --write` writes the captured files, `--out <dir>` writes them elsewhere (two runs give the same files), `--leakcheck` checks that no page text gives away a solution line or a locked hint, and `prove.py w4` re-captures and fails on any difference.
